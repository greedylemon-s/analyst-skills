# 技术尽职调查 7 维度清单（Technical DD）

系统化检查一家技术公司的"真实技术家底"，过滤包装话术。源于投资 DD 实践，但**框架本身中立**——任何需要严肃评估一家技术公司技术底色的场景都适用（投资尽调、收购、深度报道、战略对标）。

## 用法

逐维度打分（1-5）+ 标注红旗/绿旗。最后做加权综合判断。不要跳维度——跳的那一维往往就是后续踩坑的地方。

---

## 维度 1：技术架构合理性

**问什么**：技术选型是否合理？架构能否支撑当前 + 未来 3 年的业务？

**怎么验**：
- 看公开技术博客、白皮书、开源代码（如有）
- 看招聘 JD 反推技术栈（招什么人 = 用什么技术）
- 看公司是否有公开技术分享（演讲、论文、专利）

**红旗**：
- 创始团队描述技术时只能用产品语言，无法讲架构选择的 tradeoff
- 技术栈拼凑感强（混用大量小众框架，无主线）
- 关键系统依赖闭源黑盒（且未签长期协议）
- 工程团队规模与技术叙事严重不匹配（吹"全栈大模型"但只有 5 个工程师）

**绿旗**：
- 能讲清楚 3 个关键技术决策的取舍
- 技术栈与业务阶段匹配
- 早期就引入了与未来规模匹配的基础设施思路

---

## 维度 2：可扩展性（Scalability）

**问什么**：当业务/数据/用户量 10x 时，系统能撑住吗？

**怎么验**：
- 看公司目前的服务规模 vs 宣称的目标规模差几个数量级
- 看核心算法/系统的复杂度（O(n)? O(n²)? 训练成本曲线？）
- 看是否做过压力测试或有公开 case study

**红旗**：
- "我们可以无限扩展" 但说不出瓶颈在哪
- 核心成本结构与营收同比例增长（无规模效应）
- 关键依赖（如 GPU、特定供应商）有刚性瓶颈

---

## 维度 3：技术债与代码质量

**问什么**：表面光鲜的产品下面是不是一堆胶水？

**怎么验**：
- 开源仓库：commit 历史、issue 处理、PR review 质量、测试覆盖率
- 招聘 JD：是否大量招"refactor / migration / cleanup" 岗位
- 离职员工公开发言、Glassdoor 评论

**红旗**：
- 关键工程师近期密集离职
- 公司频繁"重写核心系统"
- 开源仓库没有测试、文档差、issue 长期不处理

---

## 维度 4：信息安全与合规

**问什么**：技术能不能扛住安全审查？数据合规吗？

**怎么验**：
- 是否有公开的安全事件历史
- 数据处理合规性（GDPR、《个保法》、行业特定法规）
- 安全认证（SOC2、ISO 27001 等）
- 涉敏感行业（金融、医疗、政企）需特别审查

**红旗**：
- 出过未公开但业内皆知的安全事件
- 数据获取渠道存在灰色地带
- 监管动态对其商业模式构成重大不确定性

---

## 维度 5：IP / 专利 / 开源策略

**问什么**：核心技术是不是它的？能不能告别人侵权？会不会被人告？

**怎么验**：
- 详见 `ip-landscape.md`
- 检索公司及创始团队的专利
- 检索竞争对手专利对其的覆盖
- 看其使用开源软件的合规情况（GPL 等传染性 license）

**红旗**：
- 核心技术的关键专利在前东家手里（"职务发明" 风险）
- 商业产品大量依赖 GPL/AGPL 代码却未开源
- 已收到过竞争对手的 cease-and-desist letter

---

## 维度 6：技术团队的"真实水位"

**问什么**：团队真的能做出宣称的技术吗？

**怎么验**：
- 创始 CTO / 核心技术人员的：
  - 教育背景（学校 + 导师）
  - 工业经验（前东家具体做什么，离职原因）
  - 公开产出（论文、专利、开源项目、技术分享）
- 团队规模 vs 技术叙事的匹配度
- 关键人物的"可替代性"（团队是否过度依赖单人）

**红旗**：
- CTO 简历包装严重（如"Google 工作 X 年" 实为短期实习）
- 核心论文的真实贡献度存疑（看作者顺序、看引用）
- 团队没有任何中长期技术骨干，全是项目经理

**绿旗**：
- 团队有 2 人以上独立解过这个领域的硬问题
- 创始团队 + 早期工程师的留存率高
- 团队有多元化的能力组合（不是清一色同一类背景）

---

## 维度 7：基础设施与外部依赖

**问什么**：业务的"地基"在不在自己手里？

**怎么验**：
- 看核心算力/数据/模型的来源：自研、租用、还是依赖单一供应商？
- 关键 API 依赖（如 OpenAI API、AWS 特定服务）的可替代性
- 国别风险（如美籍创始人 + 中国市场、或 Nvidia 出口管制对硬件公司的影响）

**红旗**：
- 单点依赖（如全部建立在某一家 API 之上）且无 fallback
- 跨境合规存在结构性问题
- 关键供应商谈判地位极弱

## 综合判断模板

```
维度评分（1-5）：
- 技术架构：__
- 可扩展性：__
- 技术债：__
- 安全合规：__
- IP 策略：__
- 团队水位：__
- 基础设施：__

加权总分：__/35（建议权重看场景，硬科技重 IP + 团队，SaaS 重架构 + 安全）

关键红旗（≥1 个 5 分制下打 1-2 分的维度）：
- ...

关键绿旗：
- ...

是否推荐进入下一轮 DD：是 / 否 / 有条件（条件是 ...）
```

## 用这个框架时常见的错误

1. **只看简历不看产出**。学历再好，没产出就是没产出。
2. **只看光鲜面**。Demo 漂亮不等于工程扎实。一定要找 demo 之外的证据。
3. **忽视基础设施层**。AI 公司最常踩的坑是被 API 价格涨价/政策变更摧毁单位经济。
4. **不做反向考察**。除了"为什么看好"，必须问"为什么过去 12 个月没人给到更高估值 / 没人写过深度报道"。

## Handoff 提示库

用这个框架得出 7 维度评分后，可以为下游合作者提供以下方向性提示：

### → 投资合作者（analyst-business）
- 哪些维度的低分构成投资 hard block（如 IP 不清洁、关键人员离职潮）
- 哪些红旗在 term sheet 阶段必须澄清（如关键依赖的合同期限）
- 与同期同领域已投项目的 7 维度对照，找估值锚点
- 加权时哪几维对该子赛道权重最高（硬科技重 IP+团队，SaaS 重架构+安全）

### → 媒体合作者（analyst-media）
- 哪些红旗在被广泛报道前是潜在独家选题（如未被披露的离职潮、未公开的诉讼）
- 哪些维度上"对外叙事 vs 真实情况" 落差最大——这是反共识深度报道的天然题
- 工程团队的真实水位与公司 PR 叙事的对比，往往是好故事的切口
